Separating workflows that should fail independently.

When one status covers two outcomes, the slower dependency decides what the customer sees. Split the workflow where the dependencies differ, and let each half report for itself.

Layers
Interface / service / data / operation

02 / SIM activation

01Claim

Different dependencies, different records.

A SIM that works and a courier who is late are two facts. Stored as one status, the late courier hides the working SIM. On SIM activation, activation and fulfillment ran as separate services, so one could fail without the other.

02Model

What the customer can see.

Take the logistics provider down, then switch between one record for the order and one record per service.

03Pattern

One event, two owners.

Each service subscribes to the same event and keeps its own record. Events can arrive twice, and a handler that throws gets its event again. So the record leaves pending only after the work has started. A late duplicate finds the record started and skips. That check misses two copies arriving at once, or a crash between start and the update, so start must itself be idempotent on the order id. bus and records stand for your event bus and store. The second block is the status a customer sees, read from both records. 

function subscribe(bus, service) {
  bus.on("order.placed", async ({ orderId }) => {
    await service.records.insertIfAbsent(orderId, { state: "pending" });
    const { state } = await service.records.get(orderId);
    if (state !== "pending") return;
    await service.start(orderId);
    await service.records.update(orderId, { state: "started" });
  });
}

subscribe(bus, activation);
subscribe(bus, fulfillment);
{
  "order": "SAMPLE-001",
  "activation": { "state": "activated" },
  "fulfillment": { "state": "waiting", "reason": "provider_unavailable" }
}
04Contract

What each layer can rely on.

Customer
Two statuses, each with its own reason when it waits
Services
Each retries, scales and deploys without the other
State
Separate records, keyed by the same order id
Events
One order id on every event, so the halves can be correlated
05Tradeoffs

Two records can disagree.

  • Separate records need correlating and reconciling across the boundary. Plan the check before the first mismatch.
  • Redelivered events must not start work twice. Make every consumer idempotent.
  • Do not split outcomes that must succeed or fail together. A charge and its refund belong in one transaction.
06Operating

Prove each half finishes alone.

Test
Each service completes with the other's dependency down; a duplicate event starts no second piece of work
Deploy
Services release on their own pipelines
Observe
Consumer lag per service, and orders where one half finished and the other has not, past a set age
07Scope

General practice, not a client trace.

The pattern and model are illustrative, not the client's implementation. The reported ~40% shorter activation time is on the SIM activation case.
