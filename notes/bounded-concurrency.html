Protecting downstream services with bounded concurrency.

Accepting a request is cheap. Calling the system behind it is not. Cap the calls in flight, and a burst becomes a queue you can see instead of a load the downstream has to absorb.

01Claim

Cap the work you send, not the work you accept.

Acknowledge every request at once and give it a record. Then let a fixed number of calls reach the downstream at a time. Set that number from what the downstream can take, not from how many workers you can afford to run. On the integration middleware the cap was five.

03Pattern

A semaphore and a bounded retry.

Wrap the downstream call once. Callers queue in arrival order, and transient errors back off before trying again. 

function bounded(limit, call) {
  let active = 0;
  const waiting = [];
  const next = () => {
    if (active >= limit || !waiting.length) return;
    active++;
    const { args, resolve, reject } = waiting.shift();
    Promise.resolve()
      .then(() => call(...args))
      .then(resolve, reject)
      .finally(() => {
        active--;
        next();
      });
  };
  return (...args) =>
    new Promise((resolve, reject) => {
      waiting.push({ args, resolve, reject });
      next();
    });
}

async function withRetry(fn, { attempts = 3, baseMs = 1000 } = {}) {
  for (let attempt = 1; ; attempt++) {
    try {
      return await fn();
    } catch (error) {
      if (!error?.transient || attempt >= attempts) throw error;
      await new Promise((r) => setTimeout(r, baseMs * 2 ** (attempt - 1)));
    }
  }
}

const callBilling = bounded(5, (id) => withRetry(() => billing.fetch(id)));
04Contract

What each layer can rely on.

Caller
An immediate acknowledgement with a request id, not a held-open connection
Service
Never more than the cap in flight to any one downstream
State
One record per request: pending, processing, completed or failed, with every attempt
Status reads
Answered from the record, never by asking the downstream
05Tradeoffs

The wait moves; it does not disappear.

  • A cap moves waiting from the downstream into your queue. Queue depth becomes the number to watch.
  • Retries add load at the worst moment. Back off, cap the attempts, and retry only errors you know are transient.
  • One cap shared by every downstream lets one slow system starve the others. Cap per dependency.
  • The cap is a guess until you measure the downstream. Make it configuration, not code.
06Operating

Test the cap. Watch the queue.

Test
A fake downstream that counts concurrent calls; the test fails if the count ever passes the limit
Deploy
The limit and retry policy ship as configuration per dependency
Observe
Queue depth, oldest pending age, calls in flight, retries and failures, per downstream
07Scope

General practice, not a client trace.

The pattern and model are illustrative. They are not the client's implementation, and the sweep measures nothing in production. The reported 72 h → 4 h result is on the middleware case.
